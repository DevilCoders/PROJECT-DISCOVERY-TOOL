# Security Analysis

PDT uses complementary static security analyzers and deliberately reports evidence rather than exploitability claims.

## Current capabilities
- **Secret patterns** detect private keys, more than 30 provider credential formats, credential URLs and secret-like assignments. Values are redacted and never copied into findings (see [SECURITY_ANALYZER.md](SECURITY_ANALYZER.md)).
- **Python AST security** inspects dangerous calls and selected argument semantics, resolving import aliases, without importing or executing target modules.
- **Cross-language secure-code patterns** scan every recognized source family for high-signal API patterns: dynamic code and process execution, unsafe deserialization, disabled TLS verification, unsafe C memory APIs, dynamic SQL construction, request-derived outbound HTTP destinations and filesystem paths, weak hashes, disabled JWT verification, non-cryptographic randomness for secret-like identifiers, open redirects, permissive file permissions and unsafe XML external-entity settings. Python files get the same families from the syntax tree (JWT `none` or disabled signature verification, world-writable `chmod` modes, `resolve_entities=True` and `feature_external_ges`, `random` values assigned to secret-like names, redirects to request values). Java's owner-only `setWritable(true)` and the shell entrypoint idiom `exec "$@"` are not reported. YAML loaders are judged by what they construct: `SafeLoader` and `BaseLoader` are safe, an unsafe `Loader` (by keyword or position) is CRITICAL, and `yaml.load` outside Python is MEDIUM ("YAML load whose safety depends on the library version"), because js-yaml 4 and Psych 4 load safely by default and earlier versions do not.
- **Identity intelligence** (`identity-intelligence`) inventories authentication, authorization, session and OAuth/OIDC markers. `encode`/`decode` count only on a JWT or JOSE library, and outside Python a framework counts only as a whole name on an import, `require`, `use` or include line; such framework findings are INFERRED (Python imports, read from the syntax tree, are CONFIRMED).
- **API policies** (`api-policies`) record the authentication and authorization declarations code makes (guards, roles, middleware, filter-chain rules and exemptions), with rate limits, versioning and request validation, each with its framework and scope ([Policy declarations](API_ANALYZER.md#policy-declarations)).
- **Data flow and taint** (`dataflow`) follows untrusted input from web requests and sockets (and stdin, argv and the environment in C and C++) to SQL, command, code, deserialization, template, path, SSRF, XSS, redirect, format-string and buffer sinks. Python is analysed inter-procedurally (same-module helpers) and across modules; JavaScript/TypeScript, PHP, Java/Kotlin/Scala/Groovy, Go, C#, Rust and C/C++ follow input through the file's own functions (summaries of what each parameter reaches and what each function returns) and into functions of other files whose name only one file defines. Each finding names the source, the sink and their lines, and carries the sink's attacker impact, which Markdown and HTML show as their own section. See [CODE_INTELLIGENCE.md](../architecture/CODE_INTELLIGENCE.md#4-data-flow-and-taint-dataflow).
- **Configuration and deployment analyzers** separately inspect declared risky settings such as debug mode, wildcard CORS, privileged containers, host networking and broad CI permissions; the firmware analyzer flags development image features and empty root passwords in Yocto and Buildroot configurations.
- **Local vulnerability matching** compares lockfile-resolved package versions, installed OS packages (dpkg, apk, rpm) and SBOM components with an operator-imported advisory snapshot (`--vuln-db`). The snapshot can hold OSV records, NVD feeds, GitHub advisory exports, Debian tracker and Alpine secdb data, CSAF advisories and CycloneDX vulnerabilities. CISA's Known Exploited Vulnerabilities catalog marks exploited CVEs, and VEX documents (`--vex`) record the operator's own assessments.

## Evidence and limitations
- Pattern-based findings are `INFERRED`; a match is not proof of exploitability, reachability or vulnerable runtime behavior.
- Taint flows are also `INFERRED`: static analysis cannot see run-time validation, authorization or framework escaping. Outside Python, taint follows the file's own functions and reaches functions of other files only through a function name that one file defines; receiver types are inferred only for Python.
- Generic cross-language rules are lexical heuristics. They do not replace compiler-grade SAST or framework-aware route resolution.
- Secret values are not included in reports. Findings contain file paths, line numbers and redacted excerpts only.
- PDT does not run target code or connect to target services. Vulnerability matching is offline by default and never uploads project content.

A full SAST, vulnerability intelligence, compliance or penetration-test conclusion requires separate validated analysis. Human review is required for every finding.
